# Инструкции для агентов

## Назначение

Henrik's Boss Arenas — аддон для Calamity Mod, который в последующих этапах добавит тематические арены для сражений с боссами. Этап 2 завершён исследованием архитектуры; реализация игровых систем ещё не начата. Не переходить к Этапу 3 без явного разрешения пользователя.

## Технологии и зависимости

- C#, актуальный стабильный tModLoader для Terraria 1.4.4.
- Обязательная зависимость: `CalamityMod`, объявленная через `modReferences` в `build.txt`.
- Не копировать исходный код или бинарные файлы Calamity в репозиторий.

## Архитектурные правила

- Сохранять модульную, минимальную и расширяемую архитектуру; не создавать пустые классы и абстракции без текущей потребности.
- Любое состояние будущих боёв должно быть серверно-авторитетным; клиентская логика не является источником истины.
- Учитывать выделенные серверы, синхронизацию, подключение/отключение игроков и безопасный возврат участников.
- Перед использованием незнакомого API сверять актуальную документацию и, при необходимости, исходный код. Не выдумывать API tModLoader или Calamity.

## Язык и документация

- Общаться с пользователем на русском языке.
- Имена классов, методов и переменных писать на английском языке.
- Техническую документацию вести на русском языке, если нет причины использовать английский.
- При крупных архитектурных изменениях сначала объяснять причины пользователю.

## Качество и проверка

- Для нового production-кода следовать TDD: сначала тест/проверка, затем минимальная реализация.
- После значимого изменения проверять файлы и запускать доступную сборку.
- Для локальной сборки: `dotnet msbuild HenriksBossArenas.csproj /p:TModLoaderInstallDir="<путь-к-tModLoader>"`.
- Не заявлять об успешной сборке или загрузке без фактической проверки.
- Обновлять README и `docs/` при изменении поведения, ограничений или процесса разработки.

## Git

- Не выполнять разрушительные операции (`reset --hard`, force-push, массовое удаление) без явного разрешения.
- Не вносить необоснованные изменения и не затрагивать существующие проекты.
- Перед коммитом просматривать изменения, проверять отсутствие секретов и запускать доступные проверки.
- Не создавать коммиты с непроверенными изменениями, если проверка доступна.
