# Исследование архитектуры арен — Этап 2

**Статус:** рекомендация ожидает утверждения пользователя. Код игровых систем не создавался.

## Контекст и проверенные ограничения

- Локальная среда использует tModLoader `2026.09.3.1` для Terraria `1.4.4.9`.
- tModLoader предоставляет серверное сохранение и синхронизацию данных мира через `ModSystem.SaveWorldData`, `LoadWorldData`, `NetSend` и `NetReceive`. `WorldData` — серверное сообщение для синхронизации таких данных.
- Calamity — обязательный мод. Локально доступен `CalamityMod` `2.0.4.67`; его API и поведение боссов не должны подменяться или копироваться.
- Отдельные измерения не являются нативной абстракцией tModLoader. Найденная Subworld Library — сторонний мод: её исходный код использует IL hooks, pipes и отдельные subserver-процессы на выделенном сервере.
- Calamity использует состояние основного мира, тайловые/биомные проверки и собственные глобальные состояния боссов. Поэтому перенос босса в иной мир нельзя считать совместимым без отдельного прототипа для каждого кандидата.

## Рассмотренные варианты

### 1. Временная изолированная область в основном мире — рекомендуемый вариант

**Идея.** На старте боя сервер резервирует одну заранее определённую безопасную область основного мира, сохраняет снимок изменяемых тайлов и объектов, строит тематическую арену, переносит игроков и призывает/перемещает босса в пределах этой области. По окончании сессии область восстанавливается.

**Совместимость с tModLoader и Calamity:** высокая. Босс остаётся в исходном мире, поэтому сохраняет доступ к его данным, времени, биомам, сетевой модели и логике Calamity. Исключения для боссов, которым необходима специальная локация, определяются в будущем реестре и не будут перенаправляться.

**Выделенный сервер и синхронизация:** высокая. Единственный авторитетный сервер управляет состоянием сессии и редактирует тайлы. Изменённые области и состояние сессии синхронизируются обычными средствами tModLoader; не запускаются дополнительные процессы.

**Сохранение и возврат:** снимок области и состояние незавершённой сессии должны сохраняться в данных мира. При загрузке мира незавершённая сессия восстанавливает исходную область до допуска игроков.

**Производительность:** контролируемая при ограниченном размере арен, пакетной генерации и точечной синхронизации изменённых тайлов. Нельзя пересылать или снимaть весь мир.

**Ограничения:** требуется безопасно выбрать область, не перезаписывая постройки игрока; нужно учитывать биомные проверки, границы мира, NPC/предметы/тайловые сущности и конкурентный доступ. На первом прототипе используется одна сессия и один фиксированный резервируемый участок.

### 2. Отдельный subworld через Subworld Library

**Идея.** Каждая арена — отдельный subworld, создаваемый и загружаемый через Subworld Library.

**Преимущества:** сильная изоляция тайлов и простая очистка отдельной карты; библиотека заявляет сохранение subworld рядом с основным миром.

**Недостатки:** это не нативная функция tModLoader и добавляет новую обязательную зависимость. Библиотека перехватывает сетевой код и на dedicated server запускает отдельные subserver-процессы. В её публичном issue tracker есть исправленные, но реальные проблемы мультиплеерного перехода и возврата. Для Calamity не доказано сохранение всех предположений AI о главном мире, биомах и глобальном состоянии.

**Вывод:** не подходит как базовая архитектура. Может быть повторно оценён только как изолированный технический прототип после появления конкретного босса, для которого основной мир не подходит.

### 3. Отдельный `.wld`/ручное переключение миров

**Идея.** Загружать другой мир Terraria напрямую и возвращать игроков после боя.

**Вывод:** отклонено. Публичный tModLoader API не предоставляет безопасный механизм одновременного управления несколькими мирами в одном серверном сеансе. Самостоятельное переключение затронет подключённых игроков, сохранение и сетевой цикл; это фактически попытка воспроизвести более рискованную часть Subworld Library.

### 4. Постоянные арены без восстановления

**Идея.** Сгенерировать набор арен при создании мира и никогда не очищать их.

**Вывод:** отклонено для базовой механики. Это снижает сложность снимков, но необратимо меняет мир, ограничивает свободу дизайна и не обеспечивает независимую разработку/версионирование арен. Может быть отдельной необязательной функцией в будущем, но не заменяет временную систему.

## Рекомендуемое решение

Утвердить **временные серверно-авторитетные арены в основном мире** как основу проекта.

Границы решения на следующих этапах:

1. Одна активная сессия боя на мир; повторные призывы отклоняются или обрабатываются исходной игрой до явного решения.
2. Все активные игроки мира участвуют только после серверной валидации.
3. Снимок включает только документированно поддерживаемые типы данных первой версии; сложные объекты вне области или неподдерживаемые сущности блокируют запуск, а не теряются молча.
4. Первым кандидатом будет босс без специальной отдельной локации и без жёсткой зависимости от уникальной геометрии. Его актуальная логика будет исследована непосредственно перед прототипом.
5. Реестр исключений и биомных требований составляется на следующем этапе, а не предположениями на Этапе 2.

## Уровень уверенности и непроверенное

**Высокая уверенность:** tModLoader поддерживает серверное хранение/синхронизацию состояния мира; отдельные subworld не нативны; Subworld Library реализует их через внешние hooks и subserver-процессы.

**Средняя уверенность:** область основного мира даст наилучшую совместимость с большинством боссов. Это следует из сохранения исходного мира, но требует проверки первым игровым прототипом.

**Не проверено в игре:** генерация, восстановление сложных тайловых объектов, сетевой переход игроков, поведение конкретного босса Calamity и dedicated-server сценарий. Эти проверки — работа Этапов 3–5, а не результат исследования.
